# M3b — Bing and public discoverability

Select a saved business with a bound production URL. Bing evidence and the public audit are separate from Google, launch readiness and monitoring. Refresh is explicit; startup, downloads and local dashboard polling do not call providers or submit anything. Simulations use synthetic fixtures and never contact Bing or public websites.

## Connect Bing

Open **Growth · Bing → Connect Bing Webmaster Tools**. In your own [Bing Webmaster Tools](https://www.bing.com/webmasters/) account, add/import the HTTPS site and complete ownership verification if necessary. Under **Settings → API Access → API Key**, generate a key and enter it in LaunchKit. The connector uses Microsoft's supported API-key authentication and JSON/HTTP API. It does not create accounts, create sites, install verification records or call verification APIs. OAuth is not implemented for Bing.

The key grants account-wide access, including writes, to verified sites; it is not read-only consent. LaunchKit restricts mutations to exact approved sitemap submissions. On Windows, the existing current-user DPAPI vault saves the key outside the repository. Other systems use memory or `BING_WEBMASTER_API_KEY` from a user-managed environment. Empty input preserves a saved key. Replacing the key invalidates cached evidence and pending approvals; unresolved submission history remains. Revoke/regenerate keys in Bing if needed; LaunchKit does not revoke them.

Click **Refresh Bing properties and evidence**, choose an exact verified HTTPS root site matching the production hostname, then **Use selected Bing site** and refresh. HTTP, other hosts, subpaths and unverified properties are excluded. The provider's exact spelling, including a trailing slash when returned, is retained in requests and approvals. If no property appears, add/import/verify the exact HTTPS site in Bing and refresh. Provider verification is distinct from public HTTPS availability.

## Evidence and submissions

`GetUserSites`, `GetFeeds` and `GetRankAndTrafficStats` supply independently timestamped evidence. Empty metric rows are **NO_DATA**, not zero traffic. Access, transport, quota and malformed-response errors are **UNAVAILABLE**. A successfully returned row containing zeros remains valid zero-valued evidence. Daily rows include Bing's Web, Chat, News, Images, Videos and Knowledge Panel traffic. They do not isolate AI-search citations or visitors. Bing selects the available reporting dates; LaunchKit requests no date window, fills no missing days and makes no completeness claim. Dates are converted from provider timestamps to UTC instants, preserving the actual instant rather than inventing a Pacific reporting window. The UI shows the latest 28 returned rows; the download includes every returned row.

Feed status is shown verbatim with available submission/crawl timestamps and feed URL count. Missing fields remain unavailable. A feed URL count is not an indexed-page count. URL indexing inspection remains unavailable. Evidence becomes stale after 24 hours; a fresh read can still return older provider data, whose dates remain visible.

**Prepare Bing sitemap submission** requires verified, approved M1 SEO and current Bing verification. Review the exact site and `https://your-domain/sitemap.xml`, then approve or decline. Approval is bound to business, provider, key fingerprint and target. The controller rechecks access and `GetFeeds`, saves durable intent, and calls `SubmitFeed` once. Existing listings require no new submission. **ACCEPTED** records an API response; **OBSERVED** records the provider listing. Neither proves processing or indexing. An interrupted call or ambiguous response remains **UNKNOWN** and cannot be blindly retried, even after key rotation. Refresh reconciles visible listings. No force-resubmit control is provided. The 100-record action limit blocks new approvals rather than deleting unresolved history.

## Public discoverability review

**Check public content and crawl signals** works independently of Google/Bing credentials. It reads only the bound HTTPS root, `/robots.txt` and `/sitemap.xml`, with public-address validation, DNS pinning, TLS certificate validation, timeouts, a 512 KB response limit, no cookies/credentials, and no redirect following. Each endpoint can fail independently. Reports retain findings and small observed metadata/directive excerpts, not complete response bodies or application content.

The static source scan reports canonical links, robots meta/HTTP restrictions, title/description, static body-text length, observed robots directives and sitemap locations. **OBSERVED** means a response contained the described evidence, not that a check proved SEO quality. **REVIEW** identifies a concrete item to inspect. **UNAVAILABLE** records unmeasured evidence. The revised [M3c Slice 1 audit](grow-discoverability.md) adds homepage crawler-policy interpretation and separately labeled, restricted JavaScript rendering for factual-content review. It does not validate complete HTML/XML schemas, follow child sitemaps, crawl other pages or measure indexing, ranking, visits or AI citations. Unusual markup may require manual review. No discoverability score, magic metadata or ranking guarantee is produced.

Review whether restrictions are intentional before proposing changes. M3b makes no public content or DNS changes. Approved metadata/robots/sitemap corrections can use the existing launch workflow; application content changes require review of the actual source edits before publication. No model subscription is needed.

## Storage and verification

`grow-bing/<business-id>.json` stores independent Bing state; `grow-audit/<business-id>.json` stores the latest audit. Existing `grow/` Google state and M1/M2 journals need no migration. GET reports are local reads. New POST routes retain session, Host, Origin, CSRF and shared mutation guards. API keys and provider error bodies never enter reports.

`npm run check` covers REST contracts, protected credentials, failure and empty evidence, verification filtering, approvals, crash recovery, key changes, API security and audit isolation. `npm run test:browser` covers Bing selection/submission, report downloads, audit, reload and mobile layout. These fixtures do not establish real Bing access.

For authenticated read-only acceptance, connect Bing and select the site, then run `npm run test:bing:live` with `LAUNCHKIT_LIVE_READ_ONLY=1` and `LAUNCHKIT_GROW_RUN_ID`. Optionally set `LAUNCHKIT_BING_PROPERTY` to an accessible exact site. The probe saves `bing-live-check.report.json` outside the repository. Missing credentials/access are blocked explicitly; inspect each component separately. It never submits a sitemap.
